# Windows target: design

Status: proposal, 2026-11-21, before code (todo #1046, André's decision #96 A). Owner: ablac-60. Written against master aaef105a (v0.2.65).

Sizes are S / M / L / XL by the code they touch, not by time (no durations anywhere in this plan). The order is the dependency order; one owner can run any part, and parts 2 to 4 below can run in parallel once part 1 has landed.

## Goal and non-goals

Goal, in three steps, each a release gate of its own:

1. **Programs.** `ablac build --target x86_64-windows` on Linux (and later on macOS) produces a `.exe` that runs on Windows 10 1809+ / Server 2019+ with no C runtime and no import other than `kernel32`, `ntdll`, `ws2_32` (and `bcryptprimitives` only if `ProcessPrng` is wanted, see Entropy). The standard library behaves as on Linux, except where Windows has no such thing (Unix signals, `fork`, file descriptors as integers); those are documented refusals, not silent differences.
2. **The compiler on Windows.** A static `ablac.exe` that builds, runs (`ablac run`, ORC) and self-rebuilds (stage 2 == stage 3) on a GitHub Windows runner.
3. **arm64 Windows** (`aarch64-windows`), cross-built and then native.

Non-goals: MSVC ABI interop with C++ (`extern:"c"` against the Win64 C calling convention is in scope, C++ name mangling and SEH `__try` are not); the Windows SDK as a build dependency; MinGW/Cygwin; 32-bit x86; Windows on ARM before step 3.

## What exists today (the facts the design rests on)

- Targets are `x86_64-linux`, `aarch64-linux`, `x86_64-macos`, `arm64-macos` (`bootstrapTargetDescriptor`, `src/toolchain.ab`). `bootstrapRawObjectTargetDescriptor` already accepts object format `coff`, as an object-only contract with no startup, runtime or linker (docs/targets.md). LLVM's X86 and AArch64 backends emit COFF; nothing else is needed from LLVM itself.
- **The stdlib has one system layer, the Linux syscall interface.** `abla/fs`, `abla/net`, `abla/process/*`, `abla/io`, `abla/random`, `abla/platform/host` import `abla/sys/linux/*` (about 4,350 lines: fs 660, io 130, net 2,280, process 1,235, random 50, plus entry 160), which calls the intrinsic `ablaLinuxSyscall(number, a0..a5)`. About 70 distinct syscall numbers are used (read, write, open, close, mmap, clock_gettime, getrandom, getdents64, socket and friends, poll, epoll, signalfd, fork/clone, execve, wait4, futex, ...).
- **macOS is the existing precedent for "not Linux".** The intrinsic lowers to `abla_darwin_linux_syscall` (`runtime/abla_darwin_compat.c`, 1,396 lines, 106 cases) which translates Linux syscall numbers, flags, structs and errnos to Darwin libc calls. Public modules do not know. `ablaHostIsMacOS()` is the escape hatch for the few places where the translation cannot hide the difference.
- **x86-64 Linux is libc-free** (#806): own entry, heap from `mmap` (`runtime/platform/host.ab`, 5,347 lines), futex locks, own thread creation (`abla_clone_create`), own `sigaltstack` for stack overflow, `/proc/self/maps` read by the collector to find scannable ranges. macOS and AArch64 Linux still use libc (`malloc`, `pthread_*`, `_longjmp`); AArch64 is libc-free at link time only for programs (tools/libc-imports-allowlist).
- The runtime has per-platform files: `runtime/platform/host.ab` (Linux and the libc hosts), `darwin/entry.ab` (1,578), `wasm.ab` (1,548). The Wasm runtime is the proof that a platform file can replace the host file completely.
- Panics and `try`-like unwinding use the platform's `_longjmp` (`__ablaRuntimePlatformUnwindSave/Restore`), not C++ exceptions. There is no Itanium/SEH unwind table dependence in generated code. This is the single most helpful fact for Windows: no `.pdata`/`.xdata` machinery is needed to make panics work (see Panics).
- Thread-locals in JIT and runtime code already have an emulation with no TLS directory: `abla/runtime/emutls` (381 lines, heap and atomics only). PE's `.tls` section is not needed.
- In process lld: `runtime/abla_lld_shim.cpp` (60-2) links lld's ELF and Wasm drivers into the static compiler; `LLD_HAS_DRIVER(elf)`, `LLD_HAS_DRIVER(wasm)`. The COFF driver is one more line plus `liblldCOFF.a`.

## Decision 1: how the stdlib reaches Windows

Three options.

**A. A Windows translation of the Linux syscall interface** (the macOS way): `abla_windows_linux_syscall(number, ...)` mapping Linux calls to Win32, under the unchanged stdlib.
**B. A second system layer, `abla/sys/windows`**, and every public module (`abla/fs`, `abla/net`, `abla/process/*`) picks one by target.
**C. A hybrid**: A for the calls that have a faithful Win32 counterpart, B-style native code, called through the same intrinsic boundary, for the ones that do not.

**Recommendation: C, with the translation written in Abla, not C.**

Why not pure A: Linux semantics Windows lacks (fd integers across `fork`, `epoll`, `signalfd`, `getdents` over an fd, `fork`+`execve`, `wait4`, `futex` on arbitrary words, `/proc`) are about a third of the 70 calls and are exactly the ones whose emulation is a hidden, lossy system (the Darwin shim needed 1,396 lines of C for a system that is much closer to Linux). Emulating `fork` on Windows is not possible in general; `CreateProcessW` has to replace the spawn path at the level where the stdlib decides to spawn.

Why not pure B: the public modules are about 20 places that import `abla/sys/linux`, and the Linux layer is 4,350 lines of mostly protocol logic (HTTP, TLS, DNS, directory walking, timers) layered on top of read/write/poll that is identical in shape on Windows. A full rewrite duplicates it for no gain, and every future change lands twice.

Why Abla and not C for the shim: the Windows target must build with no C compiler and no C runtime (the macOS shim is C because Darwin has a libc to call; on Windows we call `kernel32` directly, which an `extern:"c"` declaration in Abla already does). Writing it in Abla keeps the toolchain closure the same as Linux's: LLVM, lld, the Abla sources.

Shape:

- `abla/sys/linux` keeps its names (renaming the module is a separate, later and purely mechanical change; do not mix it with this work). `ablaLinuxSyscall` lowers, on a Windows target, to a call of `__ablaWindowsSyscall` in a new runtime file, as it lowers to `abla_darwin_linux_syscall` on macOS (`functions.ab:7279` is the one site).
- The handle table: a Linux fd is an index into a table of `{kind, HANDLE or SOCKET, flags, directory cursor, overlapped state}` (one page, grown on demand, lock-free fast path). fds 0, 1, 2 are the standard handles. `dup`, `dup2`, `fcntl` on fds are `DuplicateHandle` plus table entries. A table is the only way to keep `int` fds, which the whole stdlib uses as plain integers; it is also how `read` on a socket vs a file vs a pipe is dispatched (`ReadFile` vs `recv` vs overlapped).
- Calls with a faithful mapping are translated one for one: read, write, pread, pwrite, open (+ `O_*` flags to `CreateFileW` dispositions), close, lseek, fstat/stat (via `GetFileInformationByHandleEx`), ftruncate, fsync, rename (`MoveFileExW` with replace), unlink, mkdir, rmdir, getcwd, chdir, readlink (reparse points), clock_gettime, nanosleep, getrandom, mmap/munmap/madvise (VirtualAlloc/Free/DiscardVirtualMemory), exit_group, getpid.
- Calls with no mapping are listed once, with the answer the layer gives, in the stdlib's own terms: `fork`, `execve` (refused: use `abla/process/command`, see Processes), `signalfd` and signals (see Signals), `epoll` (replaced by the poll shim, see Sockets), `/proc` reads (replaced at the call sites, see GC and runtime), `chown`/`chmod` bits beyond read-only (documented partial).
- Escape hatch: `ablaHostIsWindows()` next to `ablaHostIsMacOS()`, for the few call sites (path syntax, process spawn, signals, file permission bits) where the difference belongs in the library's contract.

Size: the translation layer M to L (~2,500 lines of Abla); the call-site escapes S.

## Target triples, object format and linking

- Triples: `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`, spelled `x86_64-windows` and `aarch64-windows` in `--target`. **The `-msvc` environment, not `-gnu`**: it selects the COFF/PE conventions lld-link implements natively (no MinGW startup objects), the Win64 calling convention, `/` style linker flags, and `@feat.00` and CodeView debug-info conventions. With no CRT linked, `-msvc` and `-gnu` differ mostly in name mangling of a few symbols and stack-probe lowering (see Stack probes); `-msvc` is the better-tested LLVM path and what lld-link expects.
- Descriptor: a new `bootstrapTargetDescriptor` entry beside the four built-ins (objectFormat `coff`, pointer size 8, `hosted: true`, executable suffix `.exe`). `bootstrapRawObjectTargetDescriptor`'s `coff` path stays as the object-only contract.
- Data layout and ABI facts the backend queries by intrinsic instead of by architecture (`ablaHostValueArgumentsIndirect` is the model): the backend's `byval` handling follows the SysV x86-64 ABI. **Win64 passes aggregates larger than 8 bytes by hidden pointer and has no `byval`/red zone/`al` vararg count**; the `AblaValue`-sized aggregate (16 bytes) therefore needs the Darwin AArch64 treatment ("value arguments indirect") on Windows x86-64 too. This is one flag but touches every call site of the value ABI: **the biggest backend risk** (see Risks).
- Calling convention for `extern:"c"` into `kernel32`: LLVM `win64cc` is the default on this triple; no `stdcall` exists in 64-bit. Declarations carry `dllimport` (below) so calls go through the import address table.
- **Import libraries without the SDK.** `lld-link` links imports against `kernel32.lib`-style import libraries. We ship generated ones: a `.def` per DLL (kernel32, ntdll, ws2_32, bcryptprimitives; a few hundred names, generated from the list of functions the runtime actually declares) turned into an import library by LLVM's `llvm::object::writeImportLibrary` (`COFFImportFile`), the same code `llvm-dlltool` and `llvm-lib` use. This is C++ and lives next to `abla_archive_gnu` in the lld shim (`abla_archive_coff`, S). No Windows SDK, no `windows.h`, no `.lib` from Microsoft, so Linux hosts cross-build with nothing to download. The def files are checked in and a test compares them with `llvm-readobj` of the real `kernel32.dll` exports on the Windows lane (a name that does not exist is a load-time failure on old Windows, so the check matters).
- **lld-link in process.** `LLD_HAS_DRIVER(coff)` and `liblldCOFF.a` in `abla_lld_shim.cpp`, a `coff` branch in the shim's driver dispatch with argument 0 `lld-link`, and the link command built in `src/toolchain.ab` where the ELF one is: `/entry:abla_start /subsystem:console /nodefaultlib /nologo /machine:x64 /out:x.exe /brepro`, objects, the import libraries. Pinned lld version is the same as the ELF driver's, so output is byte-reproducible like the other targets (reproducibility test: link twice, cmp, and with `/Brepro`, which drops the PE timestamp). The external `lld-link` fallback exists exactly as `ld.lld` does for the non-static compiler.
- Debug info: CodeView needs `/debug` and PDB generation (lld-link writes the PDB itself, which makes the output depend on the PDB path). Step 1 ships without PDBs (`/debug:none`); DWARF in a COFF is accepted by lld-link and read by lldb/gdb, which is what Abla's debug story is anyway. PDBs are a later, optional item (M).
- Base relocations and ASLR: link `/dynamicbase` (default) with `/highentropy-va`; the program is position independent through the normal `.reloc`. The runtime must not hard-code addresses (see GC).

Size: descriptor and CLI S; shim and link command M; import library generator S plus the def files S; value ABI on Win64 L.

## Runtime layer over kernel32 and ntdll (no CRT)

A new platform runtime file, `abla/runtime/platform/windows/entry.ab` (modelled on `darwin/entry.ab` and `host.ab`, expected ~3,500 lines because it also contains the allocator). Everything below is `extern:"c"` + `dllimport` against a small, listed set of DLLs. A tools check (like `tools/libc-imports-allowlist.txt`) fixes the allowed import list in the repo so a new import is a reviewed change.

**Entry point.** The PE entry is `abla_start`, a naked function (no CRT means no `mainCRTStartup`; no `__chkstk` from the CRT either, see Stack probes) which: aligns the stack, calls `GetCommandLineW` and `GetEnvironmentStringsW`, converts both to UTF-8 into the runtime heap (below), stores them where `abla_runtime_set_arguments` expects them (the same place the Linux entry stores `argc/argv/envp`; `abla/process/arguments` and `environment` read from there), runs static initialisers, calls the program's `main`, and `ExitProcess(status)`s. Unlike the Linux entry this is a normal C-ABI function with a Win64 prologue; the entry is therefore written in Abla with an `@exportLocal`-like attribute, not assembly. Size S.

**Command line and environment.** Windows hands the program one UTF-16 string, not an argv. Splitting follows the `CommandLineToArgvW` rules (the quoting and backslash-before-quote rules; `shell32` is not linked, we reimplement the 40-line parser and test it against the documented table of cases). A leading `argv[0]` quirk (quoted program path) is handled. The environment block is UTF-16 `NAME=value\0...\0\0`; names are case-insensitive on Windows (`environment` lookups fold ASCII case; a documented difference), and entries starting with `=` (hidden per-drive cwd variables) are skipped. Invalid UTF-16 (unpaired surrogates, legal in Windows file names and env values) is converted to WTF-8 (surrogates encoded as three bytes) so that a round trip is lossless; strings from Windows are therefore "UTF-8 or WTF-8", and the validating string APIs (`utf8Valid`) treat WTF-8 as invalid exactly as they treat any other non-UTF-8. See Paths for what depends on it. Size S.

**Heap.** `VirtualAlloc`/`VirtualFree` replace `mmap`/`munmap`; the allocator in `host.ab` (size-class bins, large blocks mapped directly, `madvise` for returning memory) ports over with its page size hard-coded to 4 KiB and **the allocation granularity (64 KiB) respected for every `VirtualAlloc` of an address range the allocator expects to subdivide or free in parts** (Windows cannot free a part of a reservation: `VirtualFree(MEM_RELEASE)` takes the whole reservation, only `MEM_DECOMMIT` can be partial). The allocator's "trim the tail of a mapping" and `mremap` growth paths become reserve-then-commit: reserve big ranges (`MEM_RESERVE`), commit in chunks (`MEM_COMMIT`), return memory with `MEM_DECOMMIT` or `DiscardVirtualMemory`. `HeapAlloc` is not used: it adds a lock and a second allocator and the Abla heap already has its own. Large-address-aware is the default for 64-bit. Size L (the allocator is the biggest part of `host.ab`; the port is mostly the three primitive functions, but the tail-trim and `mremap` assumptions are spread).

**Threads.** `CreateThread` (not `_beginthreadex`: no CRT per-thread state to initialise) with a stack size the runtime picks, `WaitForSingleObject` on the thread handle for join, `ExitThread` at the end through the existing thread-end hook. Locks: `SRWLOCK` (`AcquireSRWLockExclusive`, ...) or the futex-style `WaitOnAddress`/`WakeByAddressSingle` (`synchronization.dll`/`api-ms-win-core-synch-l1-2-0`, Windows 8+), which is the exact analogue of the Linux futex word the runtime already uses (`__ablaRuntimeFutexLock`): **recommendation: `WaitOnAddress`**, so the lock protocol, its tests and the "slot's first eight bytes are a futex word" layout do not change. Unverified: which DLL name the import library must name (the documented one is the API-set `api-ms-win-core-synch-l1-2-0`, import library `synchronization.lib`; `kernelbase` also exports it). W1a's first probe settles it on a runner; the import allowlist then names it, and the fallback is `SRWLOCK` plus an event per waiter. Condition waits, `abla/stm` retry and parking use the same pair. Thread ids: `GetCurrentThreadId` (emutls's "is this thread still alive" check, which uses `tgkill(pid, tid, 0)` on Linux, becomes `OpenThread` + `WaitForSingleObject(h, 0)`; or better a thread-exit callback via the hook it already has, since every Abla thread passes it). Thread-locals: `abla/runtime/emutls` as is, with the one-thread-key problem (non-Abla threads) solved by FLS callbacks (`FlsAlloc` with a destructor, the Windows analogue of the pthread key destructor the macOS branch uses). Size M.

**Files and paths.** `CreateFileW` with `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE` (the POSIX-like sharing that lets us unlink or rename an open file the way the stdlib assumes), `FILE_FLAG_BACKUP_SEMANTICS` for directories, `ReadFile`/`WriteFile` (synchronous; overlapped only for sockets and pipes that `poll`), `SetFilePointerEx`, `GetFileInformationByHandleEx` (`FileStandardInfo`, `FileBasicInfo`, `FileIdInfo`), `FindFirstFileExW`/`FindNextFileW` for `entries()` (the `getdents` replacement; ordering is "sorted bytewise" already in `ablaHostListDirectory`), `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` for atomic-ish rename, `DeleteFileW`/`RemoveDirectoryW`, `CreateDirectoryW`, `GetFinalPathNameByHandleW`, symlinks and junctions through reparse points (`DeviceIoControl(FSCTL_GET_REPARSE_POINT)`). `writeTextAtomic` (temp file + rename) keeps working; deleting a file that is open without `FILE_SHARE_DELETE` elsewhere fails with sharing violations: a documented difference and a source of CI flakiness, with the retry loop in one place (`MoveFileExW` retries on `ERROR_SHARING_VIOLATION` up to a small bound, the loop Rust's std and Go's os also carry). `fs/watch` (inotify) becomes `ReadDirectoryChangesW`: M, deferrable (return "unsupported" first). `fsync`: `FlushFileBuffers`. Permissions: only the read-only attribute and executable-by-extension; mode bits are reported synthetically (documented). Size L together with the handle table.

**Paths and UTF-16.** Every API call is the `W` form; the boundary converts UTF-8/WTF-8 to UTF-16 into a stack buffer for paths under 260 and into a heap buffer otherwise, prefixing `\\?\` for paths that need it. The stdlib `Path` type is currently Unix-shaped (separator `/`, absolute means starts with `/`, `child`, `parent`, `name`). Windows needs: drive letters (`C:\`, `C:` relative-to-drive-cwd), UNC (`\\server\share`), `\\?\` and `\\.\` prefixes, both separators accepted on input and `\` produced by `toString()` on Windows (`/` always accepted: Abla programs and `build.ab` files use `/`, and **the canonical form inside Abla's own tooling (cache keys, discovery cache, build-file-relative paths) must stay `/`-separated so hashes and reproducible outputs agree across hosts**; conversion happens only at the OS boundary). Case-insensitivity of lookups: the file system decides; Abla keeps names as given, `Path` equality is the byte comparison (documented), and the module cache keys on a case-preserving, `/` normalised form. Reserved names (`CON`, `NUL`, `AUX`, ...) and trailing dots/spaces: `\\?\` avoids most; a test lane case documents the rest. Long paths: `\\?\` prefix always for absolute paths. Hidden risk: `tests/cases` and the compiler's discovery use `/`-literals in many places; an audit by grep (`"/"`, `'/'`, `.split("/")`) is the first task of the paths item. Size L (touches the compiler's own module paths and caches, not just the stdlib).

**Sockets (`ws2_32`).** Winsock is initialised once at first use (`WSAStartup(0x0202)`, no matching cleanup needed at process exit). A socket is a `SOCKET` in the handle table behind a fake fd. Mapping: `socket`, `bind`, `listen`, `accept`, `connect`, `send`/`recv`, `sendto`/`recvfrom`, `getsockname`/`getpeername`, `setsockopt`/`getsockopt` (option numbers and levels translated: Windows' `SOL_SOCKET` is 0xffff, `SO_REUSEADDR` means `SO_REUSEPORT`-like behaviour: **`SO_REUSEADDR` on Windows lets another process steal a listening port; the correct analogue of Linux's `SO_REUSEADDR` is to set nothing, or `SO_EXCLUSIVEADDRUSE` for servers**), `shutdown`, `closesocket`. Non-blocking mode via `ioctlsocket(FIONBIO)`; the stdlib's readiness model (`poll`/`epoll` on non-blocking sockets) maps to **`WSAPoll`** for the portable calls and, for the `epoll` users (the async HTTP client, the websocket server, `abla/net` event loops), to a poll-set shim over `WSAPoll` (level-triggered like epoll's default; the number of sockets is bounded by what a program has, `WSAPoll` is O(n) but correct; **IOCP is a later optimisation**, not a step-1 requirement). Known `WSAPoll` traps to design around: a failed non-blocking `connect` is reported through `POLLHUP` on older Windows (fixed from 10 1607 onward, which our baseline satisfies, and still wrapped by a `getsockopt(SO_ERROR)` check), and `WSAPoll` cannot wait on anything but sockets, so a poll over a mix of sockets and pipes/stdin needs the readiness shim to run a waiter thread for the non-socket handles or to use `WaitForMultipleObjects` for them; step 1 supports sockets-only poll plus stdin/pipe readiness through a helper thread (the `ablaHostStdinLineAvailable()` case). Unix domain sockets: Windows 10 1803+ has `AF_UNIX`; supported where Winsock supports them, `socketpair` is not (a documented absence; the stdlib's internal self-pipe wakeups use a loopback TCP pair on Windows). IPv6, UDP, multicast: same calls, address struct translation (`sockaddr` layout: Windows has no `sa_len`, the family is 16 bits like Linux, so the Linux struct layout is already right; `sockaddr_in6` and `scope_id` the same). DNS: `abla/dns` already speaks UDP/TCP to a resolver itself; Windows needs the resolver address list (`GetNetworkParams`/`GetAdaptersAddresses` in `iphlpapi`, or the registry key `Tcpip\Parameters`), and the hosts file at `%SystemRoot%\System32\drivers\etc\hosts`; today it reads `/etc/resolv.conf` and `/etc/hosts`. Size XL (the net layer is 2,280 lines and the poll shim is new).

**Processes.** `fork` is not available, so the spawn path at the library level is where the work is: `abla/process/command` today ends in `fork`/`clone` + `execve` with pipes set up between them. On Windows it calls `CreateProcessW` with `STARTUPINFOEXW` and an attribute list naming exactly the handles to inherit (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, so no handle leaks to the child, the analogue of `O_CLOEXEC` by default), pipes from `CreatePipe` with overlapped read ends for polling, `WaitForSingleObject` + `GetExitCodeProcess`, `TerminateProcess` for `kill`. Command line: the library quotes arguments into one UTF-16 command line by the inverse of the argv rules above (a tested function, round-tripped against the parser on 10,000 generated argument vectors in the fuzzer: a natural `tools/fuzz` family). `PATH` lookup follows Windows (current directory first for `CreateProcess` only when an explicit path; `.exe` extension appended; `PATHEXT` is not applied: documented). `supervisor`/`metrics` (reading `/proc`) need Windows replacements (`GetProcessMemoryInfo` from `kernel32` as `K32GetProcessMemoryInfo`, `GetProcessTimes`): M. The compiler's own child processes (it starts the linker when not static, `git`, test runners) go through the same path. `#811`'s fork-by-system-call machinery has no Windows meaning and is compiled out. Size L.

**Time.** `QueryPerformanceCounter`/`QueryPerformanceFrequency` for monotonic (multiply/divide by 64-bit mulhi to avoid overflow: `ticks * 1e9 / freq` overflows after about 3 hours at 10 MHz: use `(ticks / freq) * 1e9 + (ticks % freq) * 1e9 / freq`), `GetSystemTimePreciseAsFileTime` for wall time (FILETIME epoch 1601 to Unix epoch conversion), `Sleep`/`WaitForSingleObject` for sleeping, with `timeBeginPeriod` not set (default 15.6 ms granularity: `SetWaitableTimerEx` with `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` (Windows 10 1803+) for sleeps under 16 ms). Time zones: `abla/date` reads `/etc/localtime` and tzdata on Linux; Windows needs either the ICU data in `kernel32` (`GetDynamicTimeZoneInformation`, `TzSpecificLocalTimeToSystemTime`) or an embedded tzdata snapshot: the latter, because Windows zone names are not IANA names and an embedded database is the one source that gives the same answers on every host. Size M.

**Entropy.** `ProcessPrng` (`bcryptprimitives.dll`, Windows 10+; what Rust and Go now use, no handle, no failure mode) for `getrandom`; `RtlGenRandom` (`advapi32!SystemFunction036`) as the fallback is **not** carried (we require Windows 10). One extra import DLL; listed in the allowlist. Size S.

**Console I/O.** `GetStdHandle`, then `WriteFile` for output; when the handle is a console (`GetConsoleMode` succeeds), output goes through `WriteConsoleW` after UTF-8 to UTF-16 conversion (otherwise `WriteFile` of UTF-8 bytes is correct for redirected output and wrong for the console under a legacy code page); `SetConsoleOutputCP(CP_UTF8)` is the one-line alternative and is used first because it keeps the byte path (and its tests) identical, with `WriteConsoleW` only if the CP cannot be set. Input: `ReadFile` on a redirected stdin, `ReadConsoleW` for a console with the same conversion. Virtual terminal escape sequences: `ENABLE_VIRTUAL_TERMINAL_PROCESSING` set at the first write to a console so the stdlib's ANSI colours (used by the test runner and the compiler's diagnostics) work; failure is silent. Line endings: no translation anywhere (`\n` in, `\n` out). Size M.

**Panics, exceptions and stack overflow.** Panics and aborts use the existing unwinding that does not depend on the platform's exception tables (the runtime's own `Unwind Save/Restore` over `_longjmp`): on Windows the save/restore pair is implemented in the runtime in assembly-free Abla over LLVM's `llvm.eh.sjlj.setjmp`/`longjmp` (or a four-register save/restore intrinsic, which is what the `UnwindSave` call site needs: callee-saved registers rbx, rbp, rdi, rsi, r12-r15, xmm6-15, rsp, return address), **not** the CRT's `_setjmp`/`longjmp`, which on Win64 unwinds through `.pdata` and is meant to interoperate with SEH (and which we do not have without the CRT). Hardware faults (the null dereference, division by zero, stack overflow) become panics through a **vectored exception handler** (`AddVectoredExceptionHandler(1, handler)`): `EXCEPTION_STACK_OVERFLOW` (the handler runs on the faulting thread's remaining guard page region; Windows reserves a one-page-and-a-bit guard and **`SetThreadStackGuarantee`** lets the runtime ask for more, like `sigaltstack`; `_resetstkoflw` is the CRT's job of re-arming the guard page: the runtime does it with `VirtualProtect(PAGE_GUARD)`), `EXCEPTION_ACCESS_VIOLATION`, `EXCEPTION_INT_DIVIDE_BY_ZERO`, `EXCEPTION_ILLEGAL_INSTRUCTION` (trap). The handler prints the same diagnostic the Linux SIGSEGV handler prints and then either unwinds to the nearest panic frame (when one is registered for the thread) or ends the process with the same exit status the Linux path produces (**decision needed from André: the exit status of an unhandled panic on Windows**; default proposal: the same numeric status as on Linux, whatever `runtime/self` uses there, so scripts and tests agree). Windows x64 requires unwind tables (`.pdata`/`.xdata`) for any frame the OS unwinder walks. The runtime never uses the OS unwinder (it restores saved registers), and vectored handlers run before any frame-based handler, so the design does not depend on the tables; to be confirmed by the W1e fault tests. LLVM emits `.pdata`/`.xdata` for every function on this triple by default (`uwtable`); keep that (it makes debuggers and `RtlVirtualUnwind`-based profilers work) and test with the unwind-info present. `SIGINT` is `SetConsoleCtrlHandler`: see Signals. Size L, **and the highest-uncertainty runtime item**: the stack-overflow-in-a-thread-other-than-main path and the guard re-arming need a real Windows machine to verify, not Wine (Wine's handling of `EXCEPTION_STACK_OVERFLOW` is partial).

**Signals.** Unix signals do not exist. The stdlib's `abla/process/signal` offers: terminate-requested (SIGINT/SIGTERM), child exit, pipe closed, user signals. Windows mapping: `SetConsoleCtrlHandler` for Ctrl-C and Ctrl-Break and console close (delivered on a new thread: the handler posts to the runtime's existing signal-queue and returns, so the semantic is "an event the program polls", which is how the Linux `signalfd` path already presents it); SIGTERM from another process is `TerminateProcess` (no handler possible: documented); `SIGPIPE` does not exist (a write to a closed pipe is an error return, which is what Abla wants anyway); `SIGCHLD` is replaced by waiting on the child's process handle (the supervisor already waits per child); user signals: unsupported (`signal.send` refuses). Documented, tested as refusal. Size M.

## What in the stdlib is Linux- or macOS-specific, and how it maps

| Area | Where | Windows treatment |
|---|---|---|
| Syscall layer | `abla/sys/linux/*` (4,350 lines) | The intrinsic lowers to `__ablaWindowsSyscall`; translation in Abla (Decision 1). |
| Files, directories | `sys/linux/fs`, `abla/fs`, `fs/secure`, `fs/watch` | Handle table, `CreateFileW` family, `FindFirstFileExW`; `fs/watch` -> `ReadDirectoryChangesW` (deferred). Secure file ops that rely on `O_NOFOLLOW`/`openat`/`fchmodat` (`fs/secure`) get `FILE_FLAG_OPEN_REPARSE_POINT` and `NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory` (this is the one place `ntdll` is needed directly: `openat`-like relative opens). |
| Standard streams, TTY | `sys/linux/io`, `abla/io` | Console API as above; `isatty` = `GetConsoleMode`. |
| Sockets | `sys/linux/net` (2,280 lines), `abla/net`, `net/hosted`, `http`, `websocket`, `tls/hosted` | `ws2_32` + poll shim; TLS libraries are sans-IO (`tls/pure`) and carry no OS dependence: they run unchanged; `tls/hosted` only touches sockets and the root store: **system root certificates** on Windows come from the certificate store (`crypt32!CertOpenSystemStoreW`) or from a shipped bundle; shipping the bundle is the default (same as Linux reading `/etc/ssl`), the store reader is a later option. |

| Device, `/dev`, `/sys`, `/proc` readers | `abla/device`, `process/metrics`, `platform/host` (`/sys/devices/system/cpu/online`, `/proc/self/maps`) | `GetSystemInfo`, `K32GetProcessMemoryInfo`; `ablaHostProcessorCount` is the one `/sys` read in the host API. |
| Dynamic loading, JIT | `abla/llvm`, ORC (`src/orc_*.ab`, `ct_native*.ab`) | Part of step 2 (the compiler); programs do not need it. |

## GC and runtime self code that assume POSIX

The collector and `runtime/self/entry.ab` (4,267 lines) are mostly target independent (they read the heap's own registry), but these are POSIX-specific and are each a named item:

1. **Scannable ranges from `/proc/self/maps`** (`host.ab:1977` and `:2736`): the conservative scan walks the process's writable mappings. Windows: enumerate with `VirtualQuery` over the address space (committed, `PAGE_READWRITE`/`WRITECOPY`, not `PAGE_GUARD`, not `MEM_IMAGE` read-only), merged as today; cheaper and more precise: the runtime already tracks its own heap blocks, and the **static data of the image** (`.data`/`.bss` of the exe) is found from the PE headers in memory (`__ImageBase` + section table), the thread stacks from the thread list (`NtCurrentTeb()->StackBase/StackLimit`, readable in the entry and recorded per thread by the runtime's own thread start). So Windows can scan **exact roots** (image data + registered stacks + heap), which is better than the Linux `maps` approach; keep the "ranges merged in address order" interface. Size M.
2. **Stack scanning and stop-the-world.** `host.ab:1146` records that a stop-the-world collection for programs with threads is "a separate project": threads stop by cooperation, not by signals. Windows has `SuspendThread` + `GetThreadContext`, a stronger primitive than Linux's, but the existing cooperative protocol does not need it; **keep the cooperative protocol first** (same code, `WaitOnAddress` instead of futex) and treat preemptive suspension as an option only if the Linux design changes. Stack bounds come from the TEB, not `pthread_getattr_np`. Size S given item 1.
3. **Thread start and end hooks**: `abla_clone_create` is raw `clone`; Windows is `CreateThread`. The runtime already has the thread-end hook (`__ablaRuntimeSetThreadEndHook`); the DLL-style `DllMain` thread detach is not available to an exe, so the hook stays "run by the thread's own entry function last" and threads the runtime did not start are covered by FLS callbacks (Threads section). Size covered.
4. **Alternate signal stack** (`host.ab:1052`): replaced by `SetThreadStackGuarantee` and the vectored handler (Panics). Size covered.
5. **`_longjmp`, `pthread_*` externs** (Darwin and AArch64 use libc for them): the Windows file defines the same `__ablaRuntimePlatform*` function set with Win32 and the register save/restore; the **interface** between `runtime/self` and a platform file is already `__ablaRuntimePlatform*` (see `darwin/entry.ab` vs `host.ab`), so `self/entry.ab` should not change except for the named items. Audit the interface first and write down the full list of `__ablaRuntimePlatform*` functions: this list is the Windows runtime's definition of done (it is also what makes the runtime testable without a compiler change: compile the platform file for Windows and check that every symbol `self` expects is defined). Size S for the audit.
6. **Page size, address-space and alignment constants**: 4 KiB pages are assumed in places; `VirtualAlloc` granularity is 64 KiB and reservation sizes differ; the allocator's "map exactly what was asked" assumption (it gets page-aligned results from `mmap`) needs `align_up(size, 64 KiB)` for reservations. Covered by the heap item.
7. **Pointer tagging and high-address assumptions**: user addresses on Windows x64 are below 128 TiB (47 bits), like Linux; ASLR randomizes the image base to a 64-bit address range with `/highentropy-va` (up to 2^47): **audit the places that squeeze pointers into fewer than 47 bits or compare against fixed constants**; the Android tagged-pointer notes in `host.ab:2881` show the codebase already cares. Size S audit.
8. **Compile-time evaluation (`ct_*`, `src/ct_native*.ab`) and the JIT** assume `fork`-based sandboxes in places (#811) and `mmap(PROT_EXEC)`: step 2 work (VirtualAlloc executable pages through `VirtualProtect`, no W^X conflict on Windows by default; ORC's COFF platform support is limited: **ORC on Windows uses `RTDyldObjectLinkingLayer` (RuntimeDyld), not JITLink COFF** in the LLVM version we pin unless the pinned LLVM's JITLink COFF is complete: check `llvm-config` of our fork before step 2; thread-locals use emutls already).

## Stack probes and compiler-rt builtins

Win64 requires touching stack pages in order for frames over 4 KiB. With `-msvc` LLVM emits a call to `__chkstk` (an assembly routine in the CRT or compiler-rt). With no CRT we **provide `__chkstk` ourselves**: the compiler already supplies compiler-rt-like builtins for libc-free Linux (the `bootstrapStaticLibcSymbols` family, `__extendhfsf2`, `__powi*`, 128-bit division etc. come from the static libgcc/compiler-rt). For Windows we ship `libclang_rt.builtins-x86_64.a` for `windows-msvc` (it contains `__chkstk` and `___chkstk_ms`) in the toolchain bundle, or write `__chkstk` as a naked LLVM function (eight lines, no data). `-fno-stack-probe`-style `"probe-stack"="inline-asm"` function attribute on this target is the alternative that avoids the symbol; the attribute is the first thing to try because it keeps the toolchain closure unchanged. `__chkstk` symbol is also needed by the **JIT'd** code in step 2 and must be a symbol of the compiler process. Size S, risk S.

## Test lanes

1. **Object lane (Linux, no emulator, every push).** Cross-build every `tests/cases` program that is target independent for `x86_64-windows`: object emission and link must succeed; `llvm-readobj --coff-imports` of the result is compared with the checked-in import allowlist (`tools/windows-imports-allowlist.txt`, the analogue of the libc allowlist); a check that no `msvcrt`, `ucrtbase`, `vcruntime` or `api-ms-win-crt-*` import appears (the CRT-free guarantee, enforced like the libc-free one). This lane needs no Wine and runs in the normal suite. Size S.
2. **Wine lane (Linux, local and CI).** `wine` (a pinned version from nixpkgs for local, `apt` Wine 9+ in CI, with `WINEDEBUG=-all`, a fresh `WINEPREFIX` per run on tmpfs, `wineboot --init` once, `xvfb` not needed for console programs) runs the produced `.exe`s: the existing test harness gets a `RUN_PREFIX` that is empty natively and `wine` for the lane, and compares stdout/exit status with the native Linux run for the **same program**: a differential lane in the spirit of the fuzzer (`tools/fuzz` modes already compare outputs across compilers; a Wine mode compares across OS). Wine is good enough for: arithmetic, strings, collections, files in the prefix, pipes, threads, loopback sockets, process spawning of other Windows exes. Wine is **not** the truth for: stack overflow handling, the exact sharing-violation behaviour, console APIs, `ProcessPrng` edge cases, long path edges, time resolution. Wine failures are triaged as "Wine bug" only with a Windows-runner reproduction. A suite-registered `tools/test-windows-wine.sh` skips with a visible "SKIP" when Wine is missing. Size M. **The unknown**: how much of the suite's `/bin/sh`-driven tests can be reused (they call `sh`, `cmp`, `grep` on the host, not on the target: the test script runs on Linux and only the produced `.exe` runs under Wine, which is the right split).
3. **Windows runner lane (truth).** `windows-latest` (Windows Server 2025 today; also `windows-2022` for the 1809-era baseline, and `windows-11-arm` for step 3) in `ci.yml`. A job downloads the Linux-built `.exe`s as an artifact (built in the Linux job: cross-built, so the Windows job needs no toolchain at all in step 1: it only runs, in `cmd` or `pwsh`, a runner script `tools/windows/run-tests.ps1` over the artifact and compares with the expected outputs the Linux job recorded). That keeps step 1's CI cost to a small job and makes "built on Linux, runs on Windows" literally the product claim. Native self-hosting jobs are step 2. Size M. **Risk**: PowerShell and `cmd` quoting in the runner script; keep the runner script to "execute `.exe` with arguments from a manifest file, compare bytes", written once, tested on a hello world first.
4. **Fuzzing.** Extend `tools/fuzz` with a Windows mode: the same generated program run natively on Linux and as a Windows `.exe` (Wine locally, the runner via artifact in a nightly job), outputs compared; plus new robust-fuzz targets for the Windows-only parsers (command-line splitter/quoter round trip, WTF-8 conversion round trip, path normaliser). Size M.
5. **Reproducibility.** `/Brepro` plus lld's determinism: two links, `cmp` equal; the same `.exe` built on Linux x86-64 and aarch64 hosts. S.

## Order and milestones

**Step 1: programs, cross-built from Linux.**

- W1a (S): descriptor, `--target x86_64-windows`, `LLD_HAS_DRIVER(coff)`, link command, import library generator and def files, `__chkstk` decision. Gate: a freestanding `.exe` that exits with status 7 through `ExitProcess`, run under Wine and on the runner. Object lane starts here.
- W1b (L): value ABI on Win64 (indirect aggregates), calling convention audit of every `extern:"c"` declaration the runtime uses. Gate: `abla/core` arithmetic, strings, collections without a heap (static data only), differential vs Linux.
- W1c (L): runtime platform file: entry, command line, environment, heap on `VirtualAlloc`, `__ablaRuntimePlatform*` complete. Gate: hello, args, env, allocation stress, GC collections (`tests/cases` memory tests).
- W1d (L): handle table, files, console, time, entropy; the Abla syscall translation for the faithful subset. Gate: `abla/fs` and `abla/io` tests in the lane.
- W1e (M): threads, locks (`WaitOnAddress`), FLS, emutls, STM and `Shared`/`Mutex` tests; panics, VEH, stack overflow. Gate: thread and panic tests, the stack-overflow test on the runner (Wine excepted).
- W1f (XL): sockets, poll shim, DNS resolver config, `AF_UNIX` subset, HTTP/websocket/TLS tests over loopback; processes (`CreateProcessW`), signals subset. Gate: `abla/net`, `http`, `process` suites in the lane, loopback only.
- W1g (L): paths: `Path` on Windows, the `/`-canonical rule, the grep audit of the compiler's own path handling (needed by step 2 anyway, and **landing it first, before W1d, is cheaper** because it is a pure-Linux refactor with Linux tests: `Path` splits OS syntax from canonical form without any Windows code).
- Release: tier T3 -> T2 in `docs/platforms.md`: "Windows: cross-built programs run on windows-latest in CI". `docs/targets.md` row replaced.

Recommended order inside step 1: W1g (paths, Linux-only refactor) can start immediately in parallel with W1a. Then W1a, W1b, W1c, W1d, W1e; W1f last, because it is the largest and its only dependencies are the handle table and the heap.

**Step 2: the compiler on Windows.**

- C1 (L): the static compiler for `x86_64-windows` cross-built from Linux: LLVM and lld static archives for `windows-msvc` (a prebuilt LLVM for this triple: **we build our own**, as with `llvm-aarch64-static.yml`; building LLVM+lld on a Windows runner with MSVC/clang-cl is the way upstream tests it, or cross-compiling LLVM with `clang --target=x86_64-windows-msvc` and an SDK we then must have: this decision is open, see Risks), the C++ lld shim compiled for Windows (the shim is the only C++ in the closure; it needs a C++ standard library for the target: **libc++ built for windows-msvc without the MSVC STL** is the CRT-free option and a project in itself, or the shim and LLVM link the static MSVC CRT `libcmt` and the compiler is "libc-free" only in the Linux sense). **This is the largest open design question of the whole plan** (Risks 1).
- C2 (L): compile-time evaluation and the JIT on Windows (RuntimeDyld/JITLink COFF, `VirtualAlloc` executable memory, `__chkstk` and the builtins in the process, emutls), `ablac run`.
- C3 (M): the compiler's own file/path/process use on Windows (module discovery, caches with `/` canonical keys, child processes, the shim-less external-linker fallback, `ablac.exe` finding its toolchain next to itself: `GetModuleFileNameW`).
- C4 (L): seed and fixpoint: a Windows runner builds stage 1 from the pinned seed (a Windows seed asset in the release, produced once by cross-building from Linux), stage 2 == stage 3 by cmp (PE with `/Brepro`), the suite shard that runs on Windows (a subset first: the tests registered "host-independent"), `make self-rebuild` equivalent as a script because the Makefile needs a POSIX shell: **Git Bash is on the runner image and is acceptable as a driver for the test scripts, but each `tools/test-*.sh` then runs under Git Bash's MSYS path translation, which mangles arguments starting with `/`: set `MSYS_NO_PATHCONV=1` in the lane and assume the scripts are POSIX (they already must be, dash on CI)**.
- Release: `abla-toolchain-x86_64-windows.zip`, named like the Linux and macOS toolchain archives so setup-abla maps it the same way: `bin/ablac.exe` (no launcher: it finds `share/abla` beside its image, and its PE header reserves the stack), `share/abla/{runtime,stdlib}` (`runtime/windows/imports/*.txt` become the import libraries of hosted links), `share/licenses`. `tools/package-windows-toolchain.sh` assembles it reproducibly on Linux from the linked `ablac.exe` after `tools/pe-info` checks the image (PE32+ x86-64 console, no C runtime import); `tools/release-check.sh` check 11 judges it; the Windows runner exercises it unpacked. Checksums as for the others. `docs/platforms.md` row to T1 only when the suite shard and fixpoint are required CI jobs.

**Step 3: arm64 Windows.** `aarch64-windows`: the AArch64 backend and lld COFF arm64 are LLVM-side; the Abla work is the AArch64 value ABI on Windows (Windows ARM64 passes like AAPCS64 with deviations: variadic arguments in integer registers, x18 reserved as the TEB pointer (the Darwin AArch64 backend already treats x18 as reserved, check the shared flag), `__chkstk` takes the size in x15 in units of 16 bytes), the `.pdata` format for ARM64 (LLVM emits it), `windows-11-arm` runner lane, import libraries for arm64 (the generator takes a machine type), an `arm64-windows` row. Cross-built programs first (Wine on ARM64 is not part of the lane; the runner is the truth; qemu-user cannot run Windows), then the compiler. Size L, mostly lane work once step 1 exists. Native Windows-on-ARM runners may not be available in the free tier: **unknown, check at the time**.

## Risks and unknowns (ranked)

1. **The LLVM/lld/C++ closure of the compiler on Windows (step 2).** The Linux static compiler links prebuilt LLVM and lld static archives and our own C++ shim against a libc-free runtime (the shim's C++ runtime needs are met in Linux by the static compiler's own libc replacement, `src/static_libc*`). On Windows, the C++ in LLVM and lld needs a C++ runtime (exceptions, RTTI, `operator new`, `std::` containers, `<atomic>`/threads, `std::filesystem` in LLVM's `Support`). The options: (a) link the static MSVC CRT and accept that the Windows compiler is *not* CRT-free (programs it produces still are): lowest risk, breaks the "Abla never requires libc" aim (#806) only for the compiler executable and only on Windows; (b) port our `static_libc` replacement to Win64 and build libc++ for it: large, and a project like #806 on Linux was. **Recommendation: (a) for the first Windows compiler, with the CRT-free compiler as a later, separate todo.** Needs André's decision, since #806 is his goal; I would put it to him as one question once step 1 has landed (so it is decided with evidence, not now).
2. **Win64 value ABI in the backend (W1b): measured, much smaller than feared (docs/design/windows-target-interface.md, section 5).** The backend encodes SysV assumptions (`byval`, `sret` placement, the `AblaValue` aggregate passing). One flag in the Darwin AArch64 case; Win64 differs in more places (`sret` in rcx, shadow space of 32 bytes, 16-byte aggregates by reference, `i128` in memory not registers, varargs `al`). If any code path emits raw assembly or calling-convention-sensitive intrinsics (the syscall intrinsic does), each needs a Windows variant. Mitigation: the freestanding gate in W1a and the differential lane find ABI errors immediately (they crash), and the fuzzer's `extern:"c"` mode (libc family) gets a Windows column for calling `kernel32` functions with 0 to 8 integer and float arguments.
3. **Stack overflow and fault handling (W1e).** Needs real Windows; Wine is incomplete here. Mitigation: a dedicated runner-only test; accept "stack overflow is fatal with a message" as the first deliverable and "recoverable panic" as the second.
4. **`WSAPoll` and the epoll users.** A semantic mismatch (edge vs level triggering is already level; mixed handle types are not supported by `WSAPoll`) can hide in the async HTTP client and the websocket server; those are the largest socket users. Mitigation: the poll-set shim has its own conformance test (an `epoll` test fixture run on both OSes), and the first lane runs the sockets tests with loopback only.
5. **Paths.** The `/`-canonical rule and WTF-8 touch the compiler, cache keys and `build.ab` files; a missed case is a wrong-cache or wrong-file bug that only shows on Windows. Mitigation: W1g lands first as a Linux-only refactor with a property test (round trip of generated Windows-style paths through canonicalisation and back), and a grep-audit checklist.
6. **Import-name drift and the Windows version baseline.** A function missing on Windows 10 1809 fails at load with no message. Mitigation: the def files are generated from the runtime's declarations and verified against the real DLL export tables on the runner; baseline stated (Windows 10 1809, Server 2019) in `docs/platforms.md`; `windows-2022` image lane.
7. **Wine versions and flakiness.** A Wine bug blocks the lane. Mitigation: pinned Wine, Wine lane is `required` only after it has been stable for a stretch of batches; the Windows runner lane is the gate; a Wine failure without a runner reproduction is not a release blocker.
8. **Antivirus/Defender and the runner**: first-run scans slow newly built `.exe`s and can lock them (`ERROR_SHARING_VIOLATION` on rename/delete of a just-written exe): the retry loop in the file layer is part of the design for this reason.
9. **Unknown**: `ProcessPrng` and `WaitOnAddress` availability on the Server 2019 baseline are documented; `SetThreadStackGuarantee` behaviour for non-main threads is the one I could not confirm from documentation alone and want to test first on a runner (the first thing W1e does). Windows 11 arm64 runner availability for step 3.

## Decisions (André, #104, 2026-11-21)

All four were taken as recommended:

1. **Step 2 C++ closure:** the first Windows compiler links the static MSVC CRT. Programs it builds stay CRT-free (the import-allowlist lane enforces it); a CRT-free compiler is a later, separate todo.
2. **Exit status of an unhandled panic on Windows:** the same numeric status as on Linux.
3. **Baseline:** Windows 10 1809 / Server 2019 and newer.
4. **Console encoding:** `SetConsoleOutputCP(CP_UTF8)` (and the input code page) at startup, the previous code pages restored on exit; `WriteConsoleW` only if the code page cannot be set.
